# CGV 데이터 출처

## Decisions

- 극장, 영화, 상영일, 회차, 회차별 잔여 좌석 수는 CGV의 비로그인 공개 API에서 가져온다.
- 좌석 배치(어느 좌석이 비어 있는지)는 CGV 로그인 세션으로 조회한다.
- 로그인 자동화와 좌석 배치 조회를 실제로 붙이는 일은, 그 앞 흐름이 실제 데이터 위에서 도는 것을 확인한 뒤 별도 작업 단위로 진행한다. 그때까지 좌석 배치와 로그인 확인은 조작 가능한 가짜 데이터로 다룬다.

## Boundaries

- 자격증명은 사용자가 자신이 실행 중인 앱에 직접 입력한다. 이 결정은 자격증명의 보관 방식을 정하지 않는다.
- 봇 차단이나 캡차를 우회하는 방식은 이 결정이 승인하지 않는다. 차단에 막히면 그 사실을 보고하고 멈춘다.

## Why

2026년 8월 27일 실제 CGV 사이트에서 확인한 결과, 비로그인으로 얻을 수 있는 것과 없는 것의 경계가 분명했다.

비로그인 공개 API로 회차별 잔여 좌석 수까지 나오므로 "매진된 회차에 자리가 생겼다"는 감지는 로그인 없이 성립한다. 반면 좌석 배치는 로그인 뒤에 있어, 사용자가 원하는 "중간 구역에 붙어 있는 2석 이상"이라는 조건은 로그인 없이 판별할 수 없다.

사용자는 잔여석 수만 보는 방식과 로그인해서 좌석 배치까지 보는 방식 중 후자를 택했다. 잔여 2석이 원하는 구역의 연석일 확률이 낮아, 잔여석 수만으로는 헛걸음이 잦기 때문이다. 약관 위반 소지와 계정 제한 위험을 알린 뒤 내려진 결정이다.

## Reconsider when

- CGV가 좌석 배치를 로그인 없이 노출하거나, 반대로 잔여 좌석 수까지 로그인 뒤로 옮길 때.
- 자동 조회로 계정이 제한되거나 CGV로부터 중단 요청을 받을 때.
- 공개 API의 경로나 파라미터가 바뀌어 잔여석 조회가 깨질 때.

## Still-rejected alternatives

- 잔여 좌석 수만 감시하고 좌석 확인은 사용자에게 맡김 — 로그인이 필요 없고 약관 위험도 낮지만, 잔여 2석이 원하는 구역의 연석일 확률이 낮아 헛알람이 잦다; 로그인 자동화가 막히면 이 방식으로 되돌아온다.
- 처음부터 전부 가짜 데이터 — 실제 공개 API의 동작이 이미 확인되어 미룰 이유가 사라졌다.

## Evidence worth preserving

2026년 8월 27일 확인. 모두 비로그인 상태의 GET 요청이며 200을 받았다.

- 극장 목록: `/api/v1/content/site/searchAllRegionAndSite?coCd=A420`
- 특별관 필터: 영화 목록 API의 `div=CUST_EXPO_MOVTYP_CD&attrCd=04`가 IMAX에 해당
- 영화별 상영일: `/api/v1/booking/searchSiteScnscYmdListByMov?coCd=A420&siteNo=0013&movNo=30001323`
- 회차와 잔여석: `/api/v1/booking/searchSchByMov?coCd=A420&siteNo=0013&scnYmd=20260827&movNo=30001323&rtctlScopCd=08`
  - 응답 항목: `siteNm`(극장명), `scnsNm`(상영관명), `scnsrtTm`/`scnendTm`(상영 시각), `cpSeatCnt`(총 좌석), `frSeatCnt`(잔여 좌석), `movNm`(영화명)
  - `siteNo=0013`은 용산아이파크몰, `movNo=30001323`은 오디세이
- 좌석 선택 화면 진입 시: "CGV 회원 로그인이 필요한 서비스 입니다" 안내가 뜨며 차단됨
- `robots.txt`: `User-agent: *`에 `Allow: /`. Cloudflare가 앞단에 있으나 일반 접근에 챌린지는 걸리지 않음. ClaudeBot 등 AI 크롤러는 `Disallow: /`
- 메인 공지: "용산아이파크몰 IMAX 예매 가능 매수를 한시적으로 조정합니다"
- 이용약관의 자동화 관련 조항은 모달 구조 때문에 확인하지 못함

### 2026년 8월 27일 구현 착수 시 확인한 접근 경계

같은 날 구현에 들어가면서 확인한 결과, 회차와 잔여 좌석 조회는 호출한 쪽이 어디냐에 따라 갈렸다. 요청 횟수와는 무관하다.

| 호출 방식 | 결과 |
| --- | --- |
| CGV 페이지 안에서 fetch | 200. 회차 34건과 잔여 좌석 수를 모두 받는다 |
| 서버(Node)에서 호출 | 403. 첫 시도부터 거부되며 Referer와 Origin을 붙여도 같다 |
| 브라우저 주소창으로 API 주소 직접 접근 | 403 |
| 브라우저에서 다른 오리진(localhost)으로 호출 | CORS 차단. `Access-Control-Allow-Origin` 헤더가 없다 |

403 응답은 Cloudflare가 반환하는 차단 페이지이며 본문은 "비정상적으로 CGV에 접속한 것이 확인되어 이용이 제한되었어요. 자세한 내용은 고객센터(1544-1122)로 문의해 주세요."다.

극장 목록(`searchAllRegionAndSite`)과 영화 목록(`searchAtktTopPostrList`)은 서버에서도 200이다. 조건을 고를 때 쓰는 실제 데이터는 이 둘에서 온다.

이 경계는 일시적인 제한이 아니라 구조적인 것으로 보인다. 회차·잔여석 조회는 CGV 자기 페이지에서 온 요청만 받으며, 웹앱은 서버로도 브라우저로도 그 조건을 만족시킬 수 없다. 서버 요청은 CGV가 거부하고, 브라우저 요청은 CORS가 거부한다.

이 확인으로 스펙의 수용 기준 4(실제 회차와 잔여 좌석 수 표시)는 웹앱 형태로는 성립하지 않는다.

### 2026년 8월 27일 확인한 좌석 배치 조회

로그인한 브라우저의 CGV 예매 페이지 안에서 좌석 조회 API를 호출한 결과, 좌석 단위 데이터를 그대로 받았다. 브라우저 확장의 content script는 같은 조건에서 돈다.

- 엔드포인트: `/api/v1/booking/searchIfSeatData`
- 파라미터: `coCd`, `siteNo`, `scnYmd`, `scnsNo`, `scnSseq`, `seatAreaNo`, `cusgdCd`, `custNo`
- `custNo`는 로그인한 사용자의 고객번호이며, 예매 화면에 들어가면 페이지가 자체적으로 채운다.

응답 `data.items[0].seats`는 좌석 하나당 한 항목인 배열이다. 천안펜타포트 IMAX관 2026-08-27 19:30 회차에서 167개 항목을 받았고, 그 가운데 `seatSaleYn`이 `Y`인 것이 39개였다. 예매 화면에 표시된 "39석/167석"과 일치한다.

판별에 필요한 필드는 모두 들어 있다.

- `seatSaleYn`: `Y`면 살 수 있는 자리, `N`이면 팔린 자리
- `seatRowNm`, `seatNo`: 열과 번호. 같은 열에서 번호가 이어지면 연석이다(확인한 회차에서 B5·B6, B16·B17이 나란히 비어 있었다)
- `xcoordStartVal`, `ycoordStartVal`: 좌석 좌표. y가 앞뒤, x가 좌우다. 상영관 전체 범위는 `sbord`의 좌표로 알 수 있어 앞·중간·뒤와 좌·중앙·우를 계산할 수 있다
- `szoneExpoNm`: CGV가 정한 구역 이름

이로써 "중간 구역에 2석 이상 붙어 있을 때만 알람"이라는 감시 조건이 성립한다.

조회에 필요한 조건은 **cgv.co.kr 페이지 안에서 실행될 것** 하나뿐이다. 같은 날 이어서 확인한 결과, `custNo`를 빼도 결과가 같고(좌석 167개, 판매 가능 39개), 로그인하지 않은 브라우저에서도 같은 결과가 나왔다. 로그인은 알람을 눌러 좌석 선택 화면으로 넘어갈 때만 필요하다.

### 확인하지 않은 것

- 확장의 백그라운드(service worker)에서 같은 호출이 되는지. CGV 탭 없이 감시할 수 있는지가 여기에 달려 있다.
- CGV 로그인 화면에는 캡차가 있다. 로그인 자동화는 성립하지 않으므로, 예매가 필요한 시점에 사용자가 직접 로그인한 세션을 쓴다.

### 2026년 8월 27일 확인한 상영관 등급 필드 (아이맥스 필터링)

`searchSchByMov`는 지점·영화·날짜만으로 그 지점의 모든 상영관(2D 일반관, 4DX, IMAX 등)을 함께 돌려준다. 별도로 지점·영화 목록 조회에 쓰는 `attrCd=04`를 이 엔드포인트에 붙여도 걸러지지 않는다.

실제 응답에서 상영관을 구분하는 필드는 `tcscnsGradCd`다. 용산아이파크몰에서 확인한 값:

- `01` (`tcscnsGradNm: "일반"`) — 1관·2관·5관·6관·7관·11관·15관 등 일반 상영관
- `02` (`tcscnsGradNm: "4DX"`) — 4DX관
- `03` (`tcscnsGradNm: "아이맥스"`) — IMAX관

`scnsNm`(상영관 이름) 문자열이 "IMAX관"으로 나오지만, 이건 지점마다 이름이 다를 수 있어 문자열 매칭보다 `tcscnsGradCd === "03"` 비교가 더 안정적이라고 판단해 이 필드를 썼다.

이 확인 전에는 회차 조회에서 아이맥스 여부를 걸러내지 않아, 감시 조건이 그 지점의 모든 상영관 회차를 함께 감시하는 결함이 있었다. 실사용 중 발견되어 `bookmarklet/src/cgv/api.ts`의 `fetchSchedules`에 `tcscnsGradCd === "03"` 필터를 추가했다.

### 2026년 8월 27일 확인한 이동식(장애인·동반석) 좌석 필드

좌석 배치 응답의 각 좌석에는 `seatSalfrmCd`(판매 형태)라는 필드가 있다. `stkndCd`(좌석 종류)와는 다른 필드이며, IMAX관에서 확인한 정의는 다음과 같다.

- `01` — 일반
- `02` — 좌석통제(VIP, 예약)
- `03` — 판매중지
- `04` — 이동식

용산아이파크몰 IMAX관에서 `04`(이동식)로 표시된 좌석 5석은 맨 앞줄(A열)에 몰려 있었다. 위치와 이름으로 볼 때 장애인·동반석으로 보인다. 실사용 중 이런 좌석이 알람으로 잡힌 것이 발견되어, `bookmarklet/src/cgv/api.ts`의 `fetchSeatMap`이 이 좌석을 판매 가능 여부와 무관하게 `free: false`로 취급하도록 고쳤다.

여러 IMAX관에서 좌석 종류(`stkndCd`)는 전부 "일반석"으로만 나와, 이동식 여부는 오직 `seatSalfrmCd`로만 구분할 수 있었다.

### 2026년 8월 27일 정정 — 이동식 좌석은 기본 제외, 조건마다 선택 가능

처음에는 이동식(장애인·동반석) 좌석을 무조건 감시 대상에서 뺐다. 이런 좌석이 필요한 사용자도 있을 수 있다는 지적을 받아, 조건 등록 화면에 "이동식(장애인·동반석) 좌석도 포함" 체크박스를 두어 조건마다 고를 수 있게 했다. 기본값은 미체크(제외)다.

### 2026년 8월 27일 확인한 예매 가능 날짜 조회

지점·영화별로 예매 가능한 상영일을 돌려주는 엔드포인트가 있다.

```
GET /api/v1/booking/searchSiteScnscYmdListByMov?coCd=A420&siteNo={지점}&movNo={영화}
```

응답은 `{ scnYmd: "20260827", hldyYn: null }` 모양의 배열이다. 상영이 없는 날은 배열에서 아예 빠진다.

회차 조회(`searchSchByMov`)와 달리, 여기서는 **`div`·`attrCd` 특별관 필터가 서버에서 제대로 걸린다.** 용산아이파크몰·오디세이로 실측한 결과:

- 필터 없음: 10일 (`20260827`~`20260906`, 단 `20260904`는 빠짐)
- `&div=CUST_EXPO_MOVTYP_CD&attrCd=04` (IMAX): 6일 (`20260827`~`20260901`)

필터 결과가 맞는지 회차 조회로 교차 검증했다.

- `20260901`: `tcscnsGradCd`가 `03`(아이맥스)인 회차 6개 있음 → 필터 결과에 **포함**
- `20260902`: 전부 `01`(일반관)뿐, 아이맥스 없음 → 필터 결과에서 **제외**
- `20260905`: 전부 `01`(15관 Laser)뿐 → 필터 결과에서 **제외**

즉 이 엔드포인트에 IMAX 필터를 붙이면 그 지점에서 그 영화의 **IMAX 상영이 실제로 있는 날짜만** 정확히 얻을 수 있다.

이 확인 전에는 조건 등록 화면의 날짜를 달력에서 아무 날이나 고를 수 있어서, 예매가 열리지 않은 날이나 IMAX 상영이 없는 날로도 감시 조건을 만들 수 있었다. 그런 조건은 알람이 뜰 수 없는데도 화면에는 "감시 중"으로 보였다. 실사용 중 발견되어, 날짜 입력을 이 목록에서 고르는 방식으로 바꿨다.

### 2026년 8월 27일 확인 — 상영관 종류 코드 체계가 둘이고 서로 겹친다

상영관을 사용자가 고를 수 있게 하면서, 코드 체계가 **두 가지**이고 값이 겹친다는 것을 확인했다.

**특별관 필터용 `attrCd`** (`/api/v1/booking/searchAtktTopPostrAttrList?coCd=A420`, `div=CUST_EXPO_MOVTYP_CD`):

- `03` 4DX
- `04` **IMAX**
- `06` DOLBY ATMOS
- `08` SCREENX
- `09` ULTRA 4DX

**회차 응답의 `tcscnsGradCd`** (`searchSchByMov`):

- `01` 일반
- `02` 4DX
- `03` 아이맥스
- `04` **SCREENX**

같은 `04`가 한쪽에서는 IMAX, 다른 쪽에서는 SCREENX다. `03`도 마찬가지로 4DX와 아이맥스로 갈린다. 두 체계를 매핑 테이블로 이어 붙였다면 상영관을 잘못 짚었을 것이다.

실측 근거(2026년 8월 27일, 스파이더맨-브랜드 뉴 데이 `30001192`):

- 강남(`0056`): `04=SCREENX`
- 용산아이파크몰(`0013`): `02=4DX`, `04=SCREENX`, `01=일반`
- 왕십리(`0074`): `01=일반`, `02=4DX`, `04=SCREENX`

회차 응답에는 `tcscnsGradCd`와 **`tcscnsGradNm`이 함께** 온다. 그래서 매핑 없이 응답에서 상영관 종류 목록을 그대로 만들 수 있다. 이 방식을 택했고, 그 결과 영화·지점·날짜 목록 조회에서는 특별관 필터를 걸지 않게 되었다(용산아이파크몰 기준 지점 목록이 IMAX 필터 시보다 늘어 175개가 된다).
